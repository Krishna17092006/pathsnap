# Dataset build: labels and candidates

Generated by `python -m src.build_dataset`. Train and student_test only; evaluator data is never read.

## Data decisions

1. **Labels by order-constrained route matching.** Each fix gets a position along the reference route through a monotone dynamic programme (position never moves backwards), so U-turns, loops and revisited arcs are resolved by time order instead of plain proximity. Matching cost is distance capped at 100 m.
2. **Unreliable labels are dropped, not guessed.** A fix whose matched arc is more than 100 m away is marked `fix_valid = False`: the reference route does not describe that part of the drive (EDA: trips 00000054, 00000033). These fixes are excluded from training and metrics but kept for HMM inference.
3. **Label threshold > candidate radius.** Labels use 100 m while candidates use 50 m, so the candidate miss rate is a real measurement and not 0% by construction.
4. **Duplicate arcs count as correct.** Some networks contain arcs with identical start and end nodes; a candidate that duplicates the true arc gets `label = 1`, because no model can separate identical geometry.
5. **Candidate radius = 50 m**, chosen from the miss-rate / table-size trade-off below.
6. **Fixes with no candidate within the radius** have no rows in the candidate table; they are listed in the fix table (`n_cand = 0`) so metrics and the HMM can account for them.

*Nearest-candidate Top-1* is the naive baseline: pick the geometrically nearest arc. On two-way roads both directions are equally near, so this baseline often picks the wrong direction; heading features address that.

### Low label-quality trips

Trips where more than 5% of fast fixes move against their labelled arc. Labels there are noisy (GPS jitter or a reference route that does not match the drive). They are kept in the tables; whether to exclude them from training should be decided by a cross-validation experiment.
